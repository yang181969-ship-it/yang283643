# 留言系统重构完成：从外部插件到真正属于小站的交流区
@category: 建站日志
@date: 2026-05-13
@meta: 留言系统重构

从 5 月 9 日开始，留言系统几乎成了这几天最主要的工程。

它原本只是网站里的一个页面，但越改越发现，留言区其实不是普通的静态内容。它要接收访客输入，要展示回复，要处理管理员操作，要防止误删和滥用，还要在移动端和桌面端都保持顺手。它既是前端页面，也是后端服务，还是整个小站里最接近「真实互动」的地方。

所以这几天做的事情，已经不是简单地换一套样式，而是把留言系统从一个依赖外部插件的功能，真正改成了小站自己的基础设施。

---

## 决定放弃 Waline

最早的留言系统基于 Waline。它的优点很明显：接入快，功能多，评论、回复、表情、管理后台这些东西都有现成方案。

但随着网站慢慢变复杂，问题也越来越明显。

一方面，Waline 的默认结构和样式很难完全贴合这个小站。即使可以通过 CSS 覆盖，也总有一些残留痕迹：输入框、评论卡片、身份标签、按钮布局，都像是在一个外部系统上不断打补丁。

另一方面，国内访问和性能也不够稳定。留言区需要依赖外部服务，打开速度、可用性、图片上传体验都不完全可控。尤其是当我希望做更细的交互，比如访客标签、管理员回复、前台展示规则、留言统计、首页最近留言联动时，继续围绕 Waline 改反而会越来越绕。

所以最后决定直接放弃 Waline，改成自研留言系统。

这一步相当于把留言区从「插件」变成「网站自己的模块」。

---

## 服务器准备：给留言系统一个自己的后端

为了让留言系统不再依赖第三方评论服务，这几天先把服务器环境搭了起来。

这次使用的是腾讯云香港轻量应用服务器，系统是 Ubuntu 22.04 LTS。服务器上安装了 Nginx、Node.js、npm、PM2、git、curl、unzip 和 build-essential。评论服务单独部署在：

```text
https://comment.yang181969.com
```

并且通过 Certbot 配好了 HTTPS。

这一层完成后，留言系统终于有了自己的后端入口。最开始先做了几个基础接口：

```text
GET /api/health
GET /api/comments
POST /api/comments
```

`/api/health` 用来确认服务是否在线，`GET /api/comments` 用来读取留言，`POST /api/comments` 用来提交留言。后端用 Node.js / Express 实现，数据则存在 SQLite 里。

数据库路径放在：

```text
/home/ubuntu/comment-system/data/comments.db
```

服务通过 PM2 托管，进程名是：

```text
comment-api
```

这样即使终端关闭，留言服务也能继续运行。重启、保存进程状态、查看日志也都变得比较清楚。

---

## 前端迁移：把 Waline 残留清掉

后端跑通以后，前端留言页也开始从 Waline 迁移到自研 API。

这一步的重点不是做新 UI，而是先把旧系统完整替换掉。原来的 Waline 客户端、Waline 容器、旧样式、旧交互都逐步清理掉，改成由前端自己请求：

```text
https://comment.yang181969.com/api/comments
```

页面可以正常完成：

- 读取留言列表
- 提交留言
- 显示访客标签
- 显示站长回复
- 留言分页
- 留言统计
- 首页最近留言联动
- 搜索和统计相关检查

这一阶段完成后，留言系统已经不再依赖 Waline。虽然 UI 还不是最终形态，但基本功能已经完全归到自己手里。

这个感觉很不一样。以前留言区像是嵌进来的一块外部组件，现在它终于变成了网站本身的一部分。

---

## 管理后台：能看、能回、能隐藏、能删除

基础留言功能跑通之后，下一个重点是管理后台。

留言系统如果只能接收访客留言，其实还不完整。真正能长期使用的评论系统，必须能管理内容：哪些留言要回复，哪些留言要隐藏，哪些测试数据要删除，哪些回复应该显示为站长身份。

这次给后端增加了管理员相关接口，并且在前端做了管理页面。管理员可以通过 token 登录，进入后台后查看留言列表，并对留言执行：

- 管理员回复
- 隐藏留言
- 删除留言
- 查看留言状态
- 查看回复关系

数据库也同步做了结构升级，支持了更多字段：

```text
parent_id
reply_to_id
reply_to_name
is_admin
role
status
```

其中 `status` 用来区分：

```text
visible / hidden / deleted
```

`role` 和 `is_admin` 用来区分普通访客和站长。这样前台就可以把普通留言显示为「游客」，把后台管理员回复显示为「站长」。

这一步完成后，留言系统才算真正有了管理能力。

---

## 回复系统：做成类似抖音的一层回复结构

留言系统里最容易变复杂的地方，其实是回复。

一开始的回复只能算基础版：顶级留言下面可以有回复，但如果想回复别人的回复，逻辑就不够清楚。继续做成无限嵌套也不是我想要的效果，因为层级一深，页面会变得很乱，移动端尤其难看。

最后确定的方案是类似抖音那种结构：

```text
顶级留言
  回复 A：@顶级留言作者
  回复 B：@回复 A
  回复 C：@回复 B
```

也就是说：

- 任何留言或回复都可以被回复
- 视觉上只缩进一层
- 不做无限嵌套
- 回复某条回复时，用 `@被回复人` 表达关系

对应到数据结构里，就是：

```text
parent_id      永远指向最外层顶级留言
reply_to_id    指向当前真正回复的那一条内容
reply_to_name  用来显示 @谁
```

比如回复了某条回复，前端只需要传 `reply_to_id`，后端会自动查出它所属的顶级留言，再计算正确的 `parent_id` 和 `reply_to_name`。

这个逻辑完成后，留言区的交流关系清楚了很多。它不会因为回复越多而不断往右缩，也不会丢失“我到底是在回复谁”。

---

## 输入框精简：只保留图片按钮

这次也顺手清理了留言输入框下面的工具栏。

之前展开输入框后，下面有好几个按钮：表情、图片、链接、代码、引用。看起来功能很多，但实际对这个小站来说有点重。

留言区不是论坛编辑器，也不是代码讨论区。它更像一个轻量交流的地方。表情可以直接用系统输入法，链接可以直接粘贴，代码和引用使用频率也不高。

所以这次只保留了图片按钮。

现在输入区更像这样：

```text
昵称 / 邮箱 / 网站
留言内容
图片按钮
发送留言
```

它比之前清爽很多，也更符合这个页面的定位。

---

## 本地图片上传：真正把图片发到服务器

这几天最折腾的部分，是本地图片上传。

一开始图片按钮还是外链模式，会弹出：

```text
请输入图片链接
```

但这不是真正的图片发送。真正想要的是从设备里选择图片，然后直接上传到留言系统里。

所以后端新增了：

```text
POST /api/upload
```

前端点击图片按钮后，会打开本地文件选择器。选择图片后，前端把图片传给后端，后端保存到服务器：

```text
/home/ubuntu/comment-system/uploads/
```

然后返回图片路径：

```text
/uploads/xxx.jpg
```

留言提交时再把这些路径一起写入 `images` 字段。

为了避免滥用，也加了一些限制：

- 每条留言最多 3 张图片
- 单张图片最大 3MB
- 支持 jpg / jpeg / png / webp / gif
- 不允许 svg、html、js、php、exe、zip 等危险格式
- 文件名由服务器生成，不使用用户原始文件名

这个功能做完以后，留言区终于可以真正发送设备本地图片了。

---

## 最难的一段：CORS、Nginx 和 uploads 权限

图片上传功能本身跑通以后，还遇到了一串比较典型的前后端联调问题。

第一步是 CORS。前端本地开发地址是：

```text
http://127.0.0.1:5500
```

它请求线上后端：

```text
https://comment.yang181969.com
```

这是跨域请求。最开始上传时浏览器直接报：

```text
Failed to fetch
```

后来打开控制台才确定，是后端没有允许本地开发地址。于是后端 CORS 配置里加入了：

```text
https://yang181969.com
https://www.yang181969.com
http://127.0.0.1:5500
http://localhost:5500
```

中间还因为 `app.options('*', ...)` 和当前 Express 版本不兼容，导致后端一度启动失败，Nginx 返回 502。后来把这个预检请求处理方式改掉，服务才恢复正常。

第二步是图片静态访问。图片已经成功上传到了服务器，但访问：

```text
https://comment.yang181969.com/uploads/xxx.jpg
```

一开始是 404，说明 Nginx 没有正确处理 `/uploads/`。后来在 Nginx 配置里加了：

```nginx
location /uploads/ {
    alias /home/ubuntu/comment-system/uploads/;
    access_log off;
    expires 30d;
    add_header Cache-Control "public, max-age=2592000";
}
```

这之后从 404 变成了 403，说明路径找到了，但 Nginx 没权限读。最后给 `/home/ubuntu`、`comment-system` 和 `uploads` 补了执行/读取权限，图片才终于能正常显示。

这一段大概是这几天最像真正后端工程的地方：不是代码写完就结束，而是要让浏览器、前端、后端、Nginx、文件系统权限全部连起来。

### 前台

### 后台

- 管理员可以登录

- 可以隐藏留言

- Express API 正常运行

它已经不再只是一个“能留言”的页面，而是一个完整的小型评论系统。

## 这几天的感受

这大概是目前整个网站里最复杂的一个版块。

别的页面多数是静态内容、数据渲染或者视觉设计，哪怕复杂，也主要集中在前端。但留言系统不一样。它同时牵涉到：

- 前端交互
- 后端接口
- 数据库结构
- 管理后台
- 权限控制
- 图片上传
- 静态资源访问
- 跨域
- Nginx
- PM2
- HTTPS
- 服务器文件权限

每一层都不能单独出错。前端写好了但后端没开 CORS，会失败；后端上传成功但 Nginx 没配 uploads，会失败；Nginx 路径对了但权限不够，也会失败。

所以这次做完之后，感觉它不只是一个功能完成了，更像是小站第一次真正拥有了一个完整的「动态系统」。

---

## 小结

从 5 月 9 日到 5 月 13 日，留言系统完成了一次彻底重构。

它从 Waline 迁移到了自研后端，从外部插件变成了自己的 API；从只能基础留言，变成了支持管理员后台、状态管理、抖音式回复和本地图片上传的完整模块；从一个页面功能，变成了一个真正跑在服务器上的小型系统。

这几天也让我重新意识到，个人网站并不一定只是静态页面的集合。只要愿意一点点往下搭，它也可以有自己的数据库、自己的后台、自己的服务、自己的内容规则，甚至自己的交流方式。

现在留言区终于不再像一个临时接进来的评论框了。

它更像是小站门口的一张小桌子：有人可以坐下来写几句话，贴一张图，回复另一个人；站长也可以回来看看，整理一下，认真回一句。

这大概就是我一直想要的留言系统。
